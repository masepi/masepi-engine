# masepi-engine

Независимый статический движок и сервер публикации. Этот репозиторий содержит только Go-код, тему, Docker Compose и nginx. Название, язык, домен, источник контента, TLS и эксплуатационные параметры конкретного сайта задаются через `.env`; Markdown и изображения находятся в отдельном content-репозитории.

## Как работает публикация

1. Автор делает commit и push в ветку контента.
2. GitHub отправляет подписанный webhook на `https://DOMAIN/hooks/content`.
3. Publisher быстро отвечает `202`, синхронизирует управляемый checkout и собирает новый релиз.
4. Изменившиеся Markdown конвертируются заново, неизменённый HTML переносится hardlink-файлами.
5. После успешной проверки symlink `current` атомарно переключается на новый релиз.

Резервный polling с интервалом `POLL_INTERVAL` подхватывает commit, если webhook был пропущен. Ошибка Git, Markdown или шаблона не меняет опубликованный релиз.

Публично доступен только HTTPS-порт `443`. Publisher не публикует порт на хост и доступен nginx только во внутренней Compose-сети. Сертификаты выпускаются и продлеваются внешним механизмом.

## Установка сервера

Требуются Linux, Git, Docker Engine, Docker Compose plugin, доступ текущего пользователя к Docker и уже выпущенный TLS-сертификат.

```sh
git clone git@github.com:masepi/masepi-engine.git
cd masepi-engine
cp .env.example .env
$EDITOR .env
./install.sh
```

Все переменные подробно описаны непосредственно в `.env.example`: назначение, допустимый формат и влияние каждой настройки. Движок не содержит fallback-значений для названия, языка, домена, репозитория или ветки конкретного сайта.

И движок, и content-репозиторий клонируются по SSH. Publisher получает read-only
доступ к `~/.ssh` пользователя, запустившего скрипт (в том числе через `sudo`),
поэтому используются уже настроенные на сервере ключи, `config` и `known_hosts`.
SSH URL контента автоматически строится из `WEBHOOK_REPOSITORY`; отдельной настройки
`CONTENT_REPO` нет. Git работает без интерактивных запросов: при недоступном ключе
или неизвестном host key установка завершается ошибкой. Remote самого движка также
должен быть SSH URL вида `git@github.com:owner/repository.git`.

Если `WEBHOOK_SECRET` пуст, установщик сгенерирует его, добавит в `.env`, выставит файлу права `0600` и напечатает параметры webhook. В GitHub нужно открыть `Settings → Webhooks → Add webhook` в content-репозитории и указать:

- Payload URL: напечатанный установщиком `/hooks/content`;
- Content type: `application/json`;
- Secret: напечатанный установщиком секрет;
- Event: только `push`.

## Управление

```sh
./start.sh       # запустить существующие образы и дождаться healthcheck
./stop.sh        # остановить Compose-проект
./restart.sh     # перезапустить сервисы
./update.sh      # безопасно обновить движок, пересобрать и проверить
./reload-tls.sh  # проверить nginx и перечитать продлённый сертификат
```

`update.sh` принимает только fast-forward обновления. Он собирает новый publisher, выполняет полную публикацию текущего контента новым движком и переключает сервисы только после успешных проверок. При ошибке checkout, образ и сайт возвращаются к предыдущей версии.

Push в репозиторий движка сам по себе сервер не обновляет. Push контента не выполняет `docker build` и не обновляет движок.

После продления сертификата внешний renewal hook должен выполнить:

```sh
cd /path/to/masepi-engine && ./reload-tls.sh
```

## Постоянное состояние

Состояние всегда хранится в игнорируемом каталоге `var/` рядом с Compose-файлом:

```text
var/
  content-repository/   управляемый checkout контента
  publish.lock          межпроцессная блокировка публикации
  site/
    current -> releases/...
    releases/           текущий и два предыдущих релиза
```

Каждый релиз содержит скрытый `.masepi-manifest.json`: commit контента, версию движка, SHA-256 входов, метаданные публикаций и готовый HTML для повторного использования. nginx запрещает отдачу dot-файлов.

## Инкрементальная сборка

- Изменение тела статьи пересобирает только её страницу.
- Изменение `title` или `date` также обновляет индекс раздела и `sitemap.xml`.
- Изображение или другой asset копируется или удаляется отдельно.
- Переход раздела между одной и несколькими статьями пересобирает весь раздел, поскольку меняются URL.
- Добавление или удаление раздела запускает полную сборку: его ссылка присутствует в меню всех страниц.
- Изменение темы или версии движка запускает полную сборку.
- Отсутствующий или несовместимый manifest безопасно заменяется полной сборкой.

RSS намеренно не создаётся.

## Формат контента

Весь content-репозиторий считается корнем контента. Каждый каталог первого уровня становится разделом. Разделы сортируются по имени; первый раздел публикуется на `/`. Если в разделе один Markdown-файл, статья открывается непосредственно по URL раздела. Раздел с несколькими файлами получает страницу списка.

Скрытые файлы и каталоги, включая `.git` и `.github`, не попадают в сборку. Корневые Markdown-файлы вроде `README.md` считаются документацией репозитория; публикации размещаются внутри каталогов-разделов.

```markdown
---
title: Первый пост
date: 2026-08-29
tags: [личное, разработка]
---

# Первый пост

Текст и локальная картинка:

![Подпись](photo.jpg)
```

Обязателен только `title`. Дата использует `YYYY-MM-DD` или RFC 3339, `tags` содержит необязательный список меток. URL статьи всегда определяется её путём и именем Markdown-файла, а HTML description — первым абзацем. Относительные ссылки и изображения вычисляются от файла Markdown. Raw HTML экранируется. Локальная тема включает шрифты и KaTeX без внешних CDN.

## Локальная разработка

```sh
set -a
. ./.env
set +a

go run ./cmd/masepi build \
  -content ../content-repository \
  -output dist
go run ./cmd/masepi serve -dir dist
```

Проверки:

```sh
make test
make vet
make shellcheck
```
